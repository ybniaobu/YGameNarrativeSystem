# 对话系统设计

策划写 Excel → 导出 CSV → 两种烘焙方式：**① 通用存储（JSON / binary / SQLite）+ 运行时解析**，或 **② 产物即 CSR（二进制或 JSON 存储）+ 运行时直接用**。

---

## 1. 两套方案

前半段完全一样：**策划写 Excel → 导出 CSV**。分歧点在"烘焙出什么、运行时做什么"。

### 1.1 方案 ①：通用存储 + 运行时解析

```
 策划编辑            机器生成           离线烘焙                 运行时
┌───────────┐ 导出 ┌───────────┐ bake ┌──────────────┐ 载入 ┌───────────────────┐
│ ch01.xlsx │ ───► │ *.csv     │ ───► │ binary       │ ───► │ 解析               │
│  (真源)   │      │ (审查快照) │      │ JSON         │      │ ↓ 节点表 / 边表     │
└───────────┘      └───────────┘      │ SQLite       │      │ ↓ 构建 CSR（可选）  │
                                      └──────────────┘      └───────────────────┘
```

产物是**通用数据格式**，与内存结构无关。运行时先解析成节点表/边表，再按需构建内存结构（CSR 只是其中一种选择）。

- 优点：存储与内存布局解耦，换内存结构不用重新 bake；SQLite 后端能直接用 SQL 查询；工具链和运行时共用一套数据
- 缺点：每次启动都要"解析 + 构建"，节点多时启动耗时和内存峰值都偏高

### 1.2 方案 ②：存储即 CSR

```
 策划编辑            机器生成           离线烘焙                 运行时
┌───────────┐ 导出 ┌───────────┐ bake ┌──────────────┐ 载入 ┌───────────────────┐
│ ch01.xlsx │ ───► │ *.csv     │ ───► │ JSON   (CSR) │ ───► │ 反序列化 / memcpy  │
│  (真源)   │      │ (审查快照) │      │ binary (CSR) │      │ ↓ 已是 CSR         │
└───────────┘      └───────────┘      └──────────────┘      └───────────────────┘
```

bake 期就把 CSR 数组定型，**产物本身就是最终内存布局**。运行时不构建，读进来即可用。

- 优点：启动近乎"读文件"的开销；没有中间对象，内存峰值低；产物体积小
- 缺点：格式与内存布局绑死，改结构就得重新 bake；SQLite 只能用 BLOB，不能按行查询；可读性差（得配一份 JSON 才能看）

### 1.3 对比

| 维度 | ① 通用存储 + 运行时解析 | ② 存储即 CSR |
|---|---|---|
| 产物内容 | 节点表 / 边表（关系形态） | CSR 数组（最终内存布局） |
| 运行时工作 | 解析 + 构建，每次启动都做 | 一次反序列化 |
| 启动耗时 | 随节点数线性增长 | 接近常量（主要就是读文件） |
| 内存峰值 | 较高（中间对象 + 目标结构） | 低 |
| 换内存结构 | 改运行时即可 | 必须重新 bake |
| SQL 查询 | ✅ SQLite 后端直接查 | ❌ 只有 BLOB |
| 调试可读性 | ✅ 数据就摆在那里 | ❌ 需配套 JSON / ids |
| 工具链复用 | ✅ 同一份数据 | ❌ 另出 story.db |
| 结构变更成本 | 低（后端与运行时可各自演进） | 高（改布局要升 `schema_version`） |
